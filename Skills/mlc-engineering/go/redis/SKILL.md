# Redis SOP

通用流程见 [Go 入口](../SKILL.md)，验证见 [测试](../../common/testing/SKILL.md)；key、Lua 集中位置及缓存协议以项目 `AGENTS.md` 为准。

## 数据与缓存边界
1. 确认拓扑、服务端/客户端能力，阅读 key、序列化、脚本、超时和失效路径，不预设单机或 Cluster。
2. 明确数据所有者、租户隔离、TTL、一致性窗口及失败时放行/拒绝策略。Redis 不是默认真相源，须说明持久化、故障转移及可接受数据损失。
3. 估算 key 数、值大小、热点、读写率和连接池容量；设计有界回源、负缓存及必要的 TTL 抖动，区分未命中与连接故障。
4. 沿用失效协议并覆盖单体、列表、分页和计数缓存；固定等待的延迟双删不提供强一致性。
5. 按已存数据格式处理序列化兼容，不无条件猜测或多次解码。

## 原子性与锁
- 临时状态的写入和 TTL 原子绑定，如同一次 SET 指定条件与过期；计数器首次创建也如此，并明确是否刷新窗口。
- 比较更新使用满足语义的原子命令或 Lua；脚本注明 KEYS、ARGV、返回值及复杂度，预校验输入并限制执行时长。
- 脚本或事务的原子执行不代表出错后自动回滚已执行写入；pipeline 也不是事务。
- 多键原子操作必须同 slot，仅共同操作的 key 使用同一 hash tag（如 `order:{id}:state`），评估槽热点；Lua 不能解决跨 slot。
- 锁用唯一所有权令牌原子获取并设置租约，不能 SETNX 后单独 EXPIRE；续租、释放须原子比较令牌，不能直接 DEL。
- 租约可能先于工作失效；关键外部写入结合幂等、条件更新或 fencing token，防止旧持有者继续写入。

## 批量与验证
- 传播 context，限制重试、pipeline 批次及回源并发，不让缓存故障引发无限回源。
- 巡检使用 SCAN，限制批次、速率、处理并发和删除成本；SCAN 非快照且可重复，处理须幂等，COUNT 不是严格数量上限。
- 生产热点路径不用 KEYS、无限扫描或无上限大集合读取。
- 覆盖 TTL 原子性、锁过期重入、旧持有者解锁、续租失败、Cluster slot、序列化、失效范围及重复 SCAN。
- 观察命中/回源率、P95/P99、内存、淘汰、大 key 和热点；验证超时、重试、过期及故障转移下的锁安全假设与一致性窗口。
