# Kafka SOP

通用流程、安全与验证见 [Go 入口](../SKILL.md)。业务不变量以项目 `AGENTS.md` 为准，专项验证见 [statistic](../statistic/SKILL.md)、[danmaku](../danmaku/SKILL.md)。

## 投递与顺序
1. 核对 broker/客户端能力、topic、分区键、生产确认、消费组及错误处理配置，明确协议、保留期、投递语义和允许乱序范围。
2. 按吞吐、消息大小和消费成本确定分区、批次与工作池容量；确认及重试策略匹配可靠性目标、副本与 ISR 条件。
3. 区分生产明确失败和确认超时的未知结果，按业务幂等规则重放；生产者幂等不等于端到端 exactly-once，也不保证重启后任意重发去重。
4. 同业务键使用稳定分区策略；Kafka 只有分区内日志顺序，同分区并行处理不保证副作用完成顺序，跨分区没有全局顺序。
5. 扩分区或更换策略可能改变同键映射，先评估迁移顺序风险，不盲目扩分区或重置消费位点。

## 持久化与恢复
- 先完成业务持久化，再按分区推进连续完成水位，不能越过失败的较小 offset；提交通常表示下一条待读位置，须核对客户端 API 和自动提交行为。
- 至少一次消费容忍重复，业务去重记录与副作用尽可能同事务落库；幂等键稳定标识事件，明确保留期、重复载荷及并发冲突。
- 数据库与消息双写明确一致性方案，可沿用 outbox；Kafka 事务依赖读写与 offset 配置，不能覆盖任意外部数据库副作用。
- 设计重试、暂停、死信及人工恢复，避免毒消息无限阻塞/循环；仅按已确认业务策略跳过，且死信须先可靠落地。
- 重平衡和关闭时停止接收、收敛在途任务，遵循客户端分区所有权规则提交。
- 拉取、工作池、重试及缓冲有界，处理预算匹配心跳和 poll；传播 context，保留协议与 tag，不记录敏感完整载荷。

## 验证重点
- 故障注入覆盖重复、丢确认、进程崩溃、业务写成功但提交失败、批次部分完成和提交响应丢失。
- 覆盖重平衡在途任务、毒消息和同键顺序，确认恢复流程不会越过未完成水位。
- 观察分区 lag、最老消息年龄、吞吐、P95/P99、重试率及重平衡频率，量化积压恢复能力。
